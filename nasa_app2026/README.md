# Database Fire

## Цель проекта

Подготовить данные NASA FIRMS и обучить модель, которая оценивает вероятность хотя бы одной спутниковой детекции в пространственной ячейке на следующий UTC-день.

Первый вариант задачи ограничен продолжением уже наблюдаемой активности: модель получает признаки ячейки, где сегодня было хотя бы одно обнаружение, и предсказывает обнаружения в этой же ячейке на следующий день. Такой набор не доказывает отсутствие пожара в ячейках без спутниковых записей.

## Структура папок

- `folders/` — распакованные исходные выгрузки NASA FIRMS.
- `zips/` — исходные ZIP-архивы выгрузок.
- `processed/` — результаты подготовки данных.
- `preprocess_firms.py` — основной воспроизводимый сценарий preprocessing.
- `repair_firms_numeric.py` — исправление физически недопустимых числовых значений в готовых результатах.
- `DISCUSSION.md` — вопросы, ответы и решения по выбору и реализации модели.

## Шаг 1 — Preprocessing: завершён

В обработку вошли семь CSV-файлов VIIRS и MODIS, в том числе архивные и NRT-версии. Landsat не включён в этот этап, потому что у него другая схема полей.

Выполнено:

1. Проверка типов, диапазонов координат, даты и времени UTC.
2. Поиск и удаление точных дубликатов.
3. Обработка пропусков: строки без валидных координат или времени подлежат удалению; числовые признаки заполняются средним по датчику, категориальные — модой по датчику. Поле `type`, отсутствующее в NRT-схеме, остаётся пустым, а не имитируется.
4. Исправление физически невозможных значений: 22 отрицательных `frp` и 2 невалидных `bright_t31` заменены средним соответствующего датчика.
5. Кодирование категорий: отдельные счётчики для датчиков, спутников, дня/ночи, источника archive/NRT и уровней confidence.
6. Создание равноплощадной пространственной сетки с ячейками около 1 км² и агрегация по UTC-дням.
7. Создание целевых признаков `target_next_day_detections` и `target_next_day_detected`.
8. Z-нормализация числовых признаков. Среднее и стандартное отклонение рассчитаны только на хронологической обучающей части, чтобы не использовать будущие данные.

Результаты полной проверки:

- прочитано и сохранено: 45 052 832 детекции;
- точных дубликатов: 0;
- строк с неверной структурой: 0;
- строк, удалённых из-за обязательных полей: 0;
- ячеек-дней с наблюдениями: 20 378 184;
- строк модельного набора с доступной меткой следующего дня: 20 323 153;
- временной охват: 31 декабря 2025 — 7 октября 2026.

## Шаг 2 — модель следующего дня: выполнен

Модель оценивает вероятность (0–100%) хотя бы одной детекции FIRMS в той же ячейке на следующий UTC-день. Это вероятность спутниковой регистрации, не вероятность возникновения реального пожара. По заранее заданной сумме рангов PR-AUC, Brier score и ECE на validation выбран вариант LightGBM `medium` (31 лист, глубина 7, 250 деревьев). Финальная модель обучена на всех разрешённых строках с датами признаков по 2026-07-25 включительно.

Временные части: обучение кандидатов до 2026-06-24; validation — 2026-06-25—2026-07-25; обучение калибратора — 2026-07-26—2026-08-05; выбор калибратора — 2026-08-06—2026-08-11; official test начинается 2026-08-12. На отдельной части для выбора Platt sigmoid немного превзошёл isotonic по Brier score и ECE. Test-строки не использовались при настройке модели.

На полном official test из 5 513 290 строк получены PR-AUC **0.4779**, Brier **0.10922**, ECE-10 **0.01728**. Ранее сохранённый baseline оценивался на выборке из 150 000 строк: логистическая регрессия — 0.4720 / 0.11644 / 0.03796, постоянная вероятность — 0.1618 / 0.13806 / 0.04223. Это полезный ориентир, но не парное сравнение на одинаковом полном test.

### Запуск прогноза в backend

Для backend создайте окружение и установите зависимости из `requirements-inference.txt`. `requirements-model.txt` нужен только для переобучения и сравнения моделей.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-inference.txt
```

Загрузите модель один раз при старте приложения. `predict_one` принимает отображение со всеми 27 полями `FEATURE_COLUMNS` и ISO-датой `date_utc`; лишние поля подготовленной строки игнорируются. Пропущенные, нечисловые, NaN и бесконечные признаки приводят к `ValueError`.

```python
import csv
import gzip
from firms_inference import FirmsNextDayPredictor

predictor = FirmsNextDayPredictor()
with gzip.open("processed/hotspot_grid_daily.csv.gz", "rt", encoding="utf-8", newline="") as source:
    prepared_row = next(csv.DictReader(source))
prediction = predictor.predict_one(prepared_row)
print(prediction)
```

Ответ содержит `probability` в диапазоне [0, 1], `probability_percent`, `target_date_utc` и описание события. Модели нужны те же признаки, которые создаёт preprocessing; вход должен относиться к ячейке, где детекция уже была сегодня. HTTP-контракт в проекте не задан, поэтому поставлена функция прогнозирования для встраивания в backend, а сам endpoint создаёт backend-разработчик.

Машиночитаемые метрики и разбиение находятся в `processed/model_comparison.json`; параметры модели и список полей — в `models/metadata.json`. Пошаговая передача fullstack-разработчику описана в [MODEL_HANDOFF.md](MODEL_HANDOFF.md). Новые функции и объекты описаны в `objects.md`.

## Ограничения данных

- Записи FIRMS являются спутниковыми обнаружениями, а не полным реестром пожаров.
- Отсутствие детекции может быть связано с облачностью, дымом, временем пролёта спутника или покрытием, поэтому его нельзя автоматически считать отсутствием пожара.
- Модельный набор текущей версии предназначен для прогноза продолжения активности в уже наблюдаемой ячейке. Для прогноза новых очагов потребуется отдельное правило формирования отрицательных примеров и внешние признаки, например погода, растительность, рельеф и данные о населённых пунктах.
